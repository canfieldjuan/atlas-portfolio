# PR-Gitleaks-Security-Baseline

## Why this slice exists

Issue #313 calls for a gitleaks secret scan as part of the portfolio security CI
baseline. The repo now has dependency audit CI, Dependabot, CodeQL SAST, and
protected required checks, but it still lacks a secret-scanning gate despite
handling Stripe configuration and customer CSV workflows.

## Scope (this PR)

Slice phase: Workflow/process

1. Add a security guardrails workflow with a gitleaks PR scan and a trusted-ref
   full-history scan.
2. Add an adoption baseline for the single current historical gitleaks finding,
   which is an environment-variable-name false positive, not a committed secret.
3. Use the ATLAS baseline-from-base-branch pattern so PRs cannot poison their
   own exclusions.

### Files touched

- `.github/workflows/security_guardrails.yml` — add gitleaks secret scanning.
- `docs/security/gitleaks-baseline.json` — record the current redacted adoption baseline.
- `web/plans/PR-Gitleaks-Security-Baseline.md` — document the slice.

## Mechanism

The workflow has two jobs:

1. `Gitleaks PR secret scan` runs only for pull requests. It checks out the PR
   head with full history, fetches the base ref, and resolves
   `docs/security/gitleaks-baseline.json` from `origin/${BASE_REF}` when it
   exists. During the adoption PR only, `main` has no baseline yet, so the
   workflow may use the baseline included in this PR. After merge, PRs use the
   trusted base-branch baseline rather than a modified PR-head baseline.
2. `Gitleaks full-history secret scan` runs on pushes to `main`, manual
   dispatches, and a weekly schedule. It scans the trusted full history with the
   checked-in baseline and uploads SARIF for GitHub code scanning.

The gitleaks container is pinned by digest, ported from ATLAS. Findings are
redacted in logs and reports.

The adoption baseline was generated by running the pinned gitleaks container
against current `HEAD`. It contains one historical finding in
`web/scripts/smoke-deflection-live-submit.mjs` from commit
`0555d8edba241279749d0623ca99ee7afeb09690`. Current source inspection shows the
matched line reads an environment variable name (`ATLAS_B2B_SERVICE_TOKEN`) and
does not contain a secret value.

## Intentional

- This PR adds gitleaks as its own workflow instead of folding it into
  `pre-push-audit`; secret scanning has different history and SARIF behavior.
- The PR scan uses the base-branch baseline when available. That is the important
  anti-poisoning guard from ATLAS #1623.
- The workflow uses the same pinned gitleaks container digest as ATLAS. Broader
  GitHub Actions SHA pinning remains a separate #313 slice.
- This PR does not update branch protection to require gitleaks yet. The exact
  check names should be confirmed from the first real run before adding them to
  required status checks.

## Deferred

- Requiring the gitleaks PR check in branch protection remains a repo-settings
  follow-up after the first run confirms the exact check name.
- Action SHA pinning remains a separate #313 slice.
- Full moderate-level dependency blocking remains deferred until Next ships a
  compatible patched dependency for the vendored PostCSS advisory.

Parked hardening: none
